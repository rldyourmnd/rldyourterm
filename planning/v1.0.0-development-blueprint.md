# Полная документационная схема разработки rldyourterm v1.0.0 (reset sync)

Дата: 2026-03-02
Версия: `1.0.0` (target baseline).

## 1) Назначение

Документ определяет обязательную последовательность planning -> implementation для v1.0:
- что делаем в v1.0,
- какие требования неизменяемы,
- в каком порядке закрываются этапы,
- какие артефакты обязательны,
- какие ручные проверки блокируют релиз.

## 2) Утверждённые факты v1.0

1. Приоритеты: стабильность -> AI CLI compatibility -> скорость.
2. Crash-intolerant target: recoverable faults не роняют активную shell-сессию.
3. Render modes: `cpu`, `gpu`, `auto`.
4. `auto`: bounded retry + deterministic `gpu -> cpu` fallback.
5. Shell baseline: `fish + starship`, fallback `zsh`.
6. Single-window baseline, no multiplexer in v1.
7. Settings UX: in-terminal command palette.
8. Frame pacing: monitor-driven cadence, no hardcoded FPS in primary path.
9. Release governance: manual-only (no CI gate baseline).
10. Self-authored-first: runtime logic project-owned by default, boundary dependencies only.

## 4) Step-by-step roadmap (документация -> код)

### Этап 0. Lock требований
- Финализировать `answer-lock`.
- Проверить согласованность ADR + AGENTS.
- Закрыть стартовую readiness-оценку.

### Этап 1. Архитектурный фундамент
- Зафиксировать VSA boundaries и API-контракты слоёв.
- Зафиксировать fallback/observability contracts.

### Этап 2. Интеграционный каркас
- Уточнить boundary contracts для `portable-pty`, `winit`, `wgpu`.
- Зафиксировать retry/backoff/degrade/control-stop поведение.

### Этап 3. Runtime MVP implementation
- Построить single-window runtime skeleton.
- Реализовать shell bootstrap + fallback.
- Реализовать `cpu/gpu/auto` + deterministic fallback.
- Реализовать command palette path.

### Этап 4. Stability hardening
- Добавить bounded recovery для GPU/PTY ошибок.
- Зафиксировать long-session behavior и latency guardrails.
- Выполнить ручной stress/test календарь.

### Этап 5. Release lock
- Сверить AGENTS/ADR/quality/risk/operations/traceability.
- Закрыть manual test evidence и release pack.

## 5) Acceptance переходов между этапами

Переход допустим только если:
- документы текущего этапа согласованы по precedence,
- traceability не имеет «битых» ссылок,
- риски имеют mitigation + owner,
- manual evidence заполнен для required gates,
- `bash planning/system/validate_planning.sh` проходит без ошибок.

## 6) Принцип контроля

- Любая внешняя dependency change сначала фиксируется в `planning/stack/*` и `dependency-evidence`.
- Любой новый риск фиксируется в `planning/risk/v1.0.0-risk-matrix.md`.
- При конфликте действует precedence из `AGENTS.md`.
