# v1.0.0 Release Pack (manifest-anchored governance)

Manual-only release checklist for v1.0 MVP closure with explicit HEAD-bound evidence policy.

Req anchors:
- `R-10`: no silent fallback; structured diagnostics + user-visible notice.
- `R-11`: single-window baseline remains explicit and verifiable.
- `R-12`: release governance is manual-only and evidence-backed.
- `R-13`: Claude/Codex/Gemini compatibility is a hard release gate.
- `R-06`, `R-14`: dependency governance and architecture boundaries are enforced by CI-callable scripts.

Machine-readable authority:
- `planning/operations/v1.0.0-evidence-manifest.json`

## 1) Documentation Lock

- `AGENTS.md` remains the highest project-level runtime policy.
- `planning/discovery/v1.0.0-answer-lock.md` remains aligned with ADR/quality/risk docs.
- `planning/system/traceability-matrix-v1.0.0.md` links each requirement to executable evidence paths.
- `planning/operations/v1.0.0-evidence-manifest.json` is present, valid JSON, and used as the release evidence contract.

## 2) Governance Validation Lock

Governance scripts are the canonical CI-callable gate entrypoints:

```bash
bash scripts/ci/run_e2e_governance.sh --mode ci
bash scripts/ci/run_e2e_governance.sh --mode release --manifest /tmp/rldyourterm-evidence-manifest.json
```

Release-preflight strict mode requires:
- manifest policy checks,
- `repo.head_sha` equality with `git rev-parse HEAD`,
- artifact provenance marker `repo_head_sha=<git rev-parse HEAD>`,
- artifact existence and required marker checks from manifest entries.

Recommended manifest refresh before strict validation:

```bash
python3 scripts/ci/refresh_release_evidence_manifest.py --output /tmp/rldyourterm-evidence-manifest.json
```

If compatibility artifacts must be regenerated as part of the same strict-preflight run:

```bash
bash scripts/ci/run_e2e_governance.sh --mode release --manifest /tmp/rldyourterm-evidence-manifest.json --with-matrix
```

The combined `--with-matrix` flow is ordered as:
1. generate fresh matrix/profile artifacts
2. refresh the selected manifest path
3. run strict evidence validation against that refreshed manifest

## 3) Runtime and Security Validation Lock

Required commands:

```bash
bash planning/system/validate_planning.sh
cargo check --workspace --locked
cargo test --workspace --locked
cargo clippy --workspace --all-targets --all-features --locked -- -D warnings
cargo fmt --all -- --check
bash scripts/ci/run_terminal_benchmark_smoke.sh
cargo +1.92.0 check --workspace --locked
cargo deny check bans licenses advisories sources
cargo audit
bash scripts/mvp/run_matrix.sh 3
```

Required scenario evidence markers:
- `MVP_GATE_RESULT ... status=pass ...` for `claude`, `codex`, `gemini`,
- `MVP_MATRIX_RESULT ... status=pass ...`,
- `single_window_required=1`,
- `release_governance=manual-only`.

## 4) Release Decision Rule

- `release blocked` if any required governance, quality, security, or compatibility gate fails.
- `release ready` only if strict governance mode passes against a refreshed manifest snapshot derived from `planning/operations/v1.0.0-evidence-manifest.json` at the selected release ref.

## 5) Evidence Update Policy (HEAD-bound)

- Dated "current run" statements are not authoritative without manifest anchoring.
- Each release-preparation cycle must refresh manifest data for the active repo state before final sign-off.
- Preferred refresh command for strict validation:
  - `python3 scripts/ci/refresh_release_evidence_manifest.py --output /tmp/rldyourterm-evidence-manifest.json`
- Optional in-repo baseline refresh:
  - `python3 scripts/ci/refresh_release_evidence_manifest.py`
- Fresh artifacts used for strict validation must carry `repo_head_sha=<selected HEAD>` markers.
- The manifest is validated by:
  - `bash scripts/ci/validate_release_evidence_freshness.sh --mode policy`
  - `bash scripts/ci/validate_release_evidence_freshness.sh --manifest /tmp/rldyourterm-evidence-manifest.json --mode strict`

## 6) Evidence Recording Checklist

For every release-preparation execution, record:
- selected ref/tag and resolved commit SHA,
- command transcripts and produced artifact paths,
- strict manifest validation output,
- unresolved blockers (if any), with issue links.

This document defines process and acceptance criteria only; it does not assert pass/fail status for any specific run.
